# Airfare Tracker

## Stack

- **Backend**: Python 3.12+, FastAPI, uvicorn, APScheduler (async)
- **Database**: SQLite via aiosqlite (WAL mode)
- **Flight data**: Google Flights via `fli` library (`pip install flights`)
- **Frontend**: Server-rendered Jinja2, HTMX, Chart.js (CDN)
- **Package manager**: conda (preferred), pip as fallback

## Coding conventions

- **No comments by default** — only when the WHY is genuinely non-obvious
- **No half-finished implementations** — if out of scope, say so explicitly
- **No emojis in code or UI text** unless explicitly asked
- **Python**: type hints everywhere, dataclasses for data structures, protocols for interfaces
- **Imports**: standard library → third-party → local. One blank line between groups
- **Function naming**: `snake_case`. Descriptive names, no abbreviations
- **FastAPI**: lifespan handler for startup/shutdown, APIRouter per module, dependency injection for DB connections
- **SQLite**: always use WAL mode, parameterized queries (no f-string SQL), aiosqlite for async access
- **Frontend**: Jinja2 templates (no JS framework), HTMX for interactivity, Chart.js for charts. CSS in a single file (no framework).

## Flight source architecture

- Each source implements `SearchSource` protocol from `backend/sources/base.py`
- Sources return `list[FlightResult]` — normalized, no source-specific fields
- Each source file is self-contained: one file, one source
- New sources = new file in `sources/` + register in `__init__.py` **unless
  the source is opt-in per tracker rather than global** — `KayakSource`
  (`backend/sources/kayak.py`, plan 017) is deliberately **not** registered in
  `get_sources()`; it's constructed directly wherever the per-tracker
  `kayak_enabled` flag is checked (the scheduler, once Phase 3 wires it in),
  not run unconditionally on every search cycle.

## Future me notes

- The `backend/sources/` directory is designed for pluggable sources. To add Amadeus: create `amadeus.py` implementing `SearchSource`, add to `__init__.py`, done.
- Notification delivery (email, push) is explicitly v2. The DB table and evaluation logic exist in v1 but no transport is wired.
- If the `fli` library breaks due to Google page changes, the fix is isolated to `backend/sources/google_flights.py`.
- **`KayakSource` (`backend/sources/kayak.py`, plan 017)**: renders `kayak.com` with a **headful patchright** Chromium (see the evasion-bundle note below; it was headless Playwright through plan 017) and extracts flights via an LLM (DeepSeek, OpenAI-compatible API — key in `os.environ["DEEPSEEK_API_KEY"]`, read at call time, never at import time). `patchright`/`openai` are imported **lazily inside `_render`/`_extract`**, not at module load, specifically so unit tests can mock those two methods and exercise `search()`'s control flow without either package installed (real installs land via `RUN patchright install --with-deps chromium` in the Docker image). Every extracted price is grounded against the rendered page text in `_validate` before being trusted (`historical_best_price` is `MIN` over all rows and never recomputed — a hallucinated cheap price is permanent). `_LLM_MODEL` / `_LLM_BASE_URL` in `kayak.py` point at **opencode.ai**, not DeepSeek's own API — `os.environ["DEEPSEEK_API_KEY"]` is a misleading name kept for minimal diff, but the value in `.env` is actually an **opencode.ai subscription key**. `_LLM_BASE_URL = "https://opencode.ai/zen/v1"` and `_LLM_MODEL = "mimo-v2.5-free"` — Zen, **not** the Go proxy, whose `deepseek-v4-flash` hit a regional gate and then a monthly cap. **The model was picked by measurement, not preference** (plan 019 Phase 3b, `.agent/reports/019-phase-3b.md`: 200 offline replays, 4 candidates × 5 captured bodies × 10 runs). The rejected incumbent `deepseek-v4-flash-free` was accurate but slow in a way nothing here could fix: **the Zen proxy honours `extra_body={"thinking": {"type": "disabled"}}` only ~3 times in 10, non-deterministically**, and a thinking run burns 2,700–7,000 completion tokens to emit ~300 tokens of JSON. Completion tokens are the tell, and they are the reason for the swap: **mimo emitted only 509 or 523 tokens across all 50 runs** — two values, never a reasoning burst — so the flag cannot be ignored, because there is no reasoning mode to ignore it with. `_extract` still sends the flag (free insurance if that ever changes; pinned by a test) and still trims the body via `_results_section` (a full ~20k-char body measured 103s). **`_LLM_TIMEOUT_S = 60.0`** (was 30) fits mimo's measured 4.3–58.7s span, whose tail is network rather than reasoning — the two slowest runs returned the same 523 tokens as the fastest. That is ~2% headroom over the observed max; past it the search returns `[]` at WARNING and the next cycle retries. **The correctness trap when benchmarking extraction models**: Kayak prints `12:30 am – 5:40 pm`, and a model that reads that as 12:30 pm produces a value that parses, survives `_canonical_timestamp`, grounds its price — and is a *second `flight_key` for one physical flight*. `longcat-2.0-free` looked like the winner on latency alone (max 13.1s, tightest tail measured) and does this on 22% of runs. `scripts/kayak_model_benchmark.py`'s `_time_grounded` is the check that caught it, and plan 019 task 4.0 ported it into production `_validate`, which now drops any row whose departure **or** arrival clock time is absent from the body (measured identical to the benchmark's verdict on all 204 real replay records; it drops 1 of mimo's 250 rows, the residual misread). Two deliberate abstentions, both so the check cannot become the thing that destroys good data: an **unparseable** time is *kept* (`_canonical_timestamp` stores such a row on purpose — this check targets the misread, not parseability), and a body printing **no** recognisable clock time grounds nothing. On a 24-hour page (a pt-BR force-redirect prints `00:30`) it grounds against the 24h form instead — but the **12-hour probe runs first and wins**, because on a page printing `12:30 am` a bare `12:30` lookup matches that very line and waves the misread through. Not registered in `sources/__init__.py::get_sources()` — see "Flight source architecture" above. `search()` sets `last_error`/`last_error_level = "WARNING"` whenever `_validate` drops rows — **all** dropped (empty result, would otherwise look identical to a clean "no flights" success) or only **some** dropped (result still returned, but the message names the drop count) — because this project's observability is the `system_logs` table on `/monitor`, and `_validate`'s own `logger.warning` calls never reach it (nothing configures a stdlib logging handler that writes there). `_OVERALL_TIMEOUT_S` is derived from `_WORKER_TIMEOUT_S`/`_LLM_TIMEOUT_S` (not a bare constant) because the render step alone can consume the child's whole budget before the LLM call even starts — if changing any render/LLM timeout, the overall cap recomputes automatically, but re-check the arithmetic still leaves slack.
- **Startup no longer re-searches everything (2026-08-11, `main.py::_tracker_is_overdue`)**: `_startup` registered every job with `run_immediately=True`, so every `--reload` — i.e. every edit under `backend/` — fired a live search for every active tracker. Measured: **144 snapshots in one day against ~24 expected** at 60 min x 6 trackers, 78 of them in the single hour spent editing code, against a source that had already returned zero rows once that night. Now the immediate run happens only when that tracker's latest snapshot is already older than its interval, so a genuine restart after downtime still refreshes at once while an edit-reload cycle stays silent. Missing or unparseable timestamps err toward searching. Pinned by `tests/test_kayak_dedupe_and_startup.py`.
- **Kayak lists one itinerary once per FARE BRAND (2026-08-11)**: observed on GRU-GVA — two rows sharing `7:20 pm – 10:25 pm+1` at €641, differing only by carrier list (`"LATAM Airlines, Iberia"` vs `"LATAM Airlines"`) and brand (`"Light + Economy Cabin"` vs `"Light"`). `_first_carrier` collapses the first difference by design and `flight_key` carries no brand, so both arrive indistinguishable. `_dedupe_rows` collapses rows identical in carrier + both clock times + price, and `_OVERFETCH_ROWS` (2) compensates because **the duplicate consumed a slot on the PAGE**, inside `_results_section`'s top-N slice, before extraction — deduping alone would have returned `top_n - 1` rows. **Neither source exposes a baggage allowance** (checked live: Kayak prints bag text only in its filter sidebar plus *"Prices ... do not include baggage fees"*; `fli`'s `FlightResult`/`FlightLeg` have no baggage field, and `BookingOption.fare_name` needs an extra call). Both *do* accept it as a **search constraint** — `fli` has `BagsFilter` and `exclude_basic_economy`, Kayak has the equivalent UI filter — so comparability is best bought by constraining the query, not by parsing. See `TODO.md`.
- **Sources are BLENDED per source, not read from one snapshot (2026-08-11, `pages.py::_build_detail_context`)**: sources run on independent cadences and fail independently, so "the latest snapshot" is only the latest view from whichever sources happened to run. A Google-only cycle used to mark Kayak's rows **"missing"** — which asserts those fares vanished, when the truth was only that Kayak had not run — and because the missing-row reconstruction looked back **exactly one snapshot**, two Google-only cycles in a row dropped Kayak from the page entirely. That is why Kayak results appeared never to show up. Now `get_source_observations(tracker_id, per_source=2)` (db.py, a `ROW_NUMBER() OVER (PARTITION BY source)` window query) returns each source's two most recent observations; the page unions each source's latest rows, computes deltas **per source** against that source's own previous run, and drops a source older than `2 * interval_minutes`. **Blend by GROUP, not raw source**: `_BLEND_GROUPS` folds `fast_flights` into `google` because `FallbackSource` runs the secondary only when the primary is empty — they are alternate scrapers of one upstream, and blending them apart resurrected a stale fallback set beside fresh primary rows (same flights, two ages). **This is a read-time join and nothing is written**: carrying rows forward into new snapshots would fabricate chart points, and `historical_best_price` is `MIN` over all rows and never recomputed, so a re-inserted stale price would distort the all-time low permanently. `best_price` is the cheapest across the blended set with `best_price_is_stale`/`_age_minutes`/`_source` driving a `.price-age` badge — **this also resolves the headline-oscillation follow-up deferred by plans 019/020**, which was the same root cause. Pinned by `tests/test_blended_sources.py`. One orchestrator test was rewritten for the new model with the user's explicit approval (`test_a_source_that_did_not_run_keeps_reporting_its_own_last_view`, replacing `test_missing_flight_reconstruction_uses_cheapest_historical_price`); its surviving intent lives in `test_missing_row_still_uses_the_cheapest_quote_of_its_own_source`.
- **Two silent source degradations (2026-08-11, both fixed)**: (1) **`FallbackSource` hid fli failures.** It returned `fast_flights`' rows without setting `last_error`, and the scheduler only writes to `system_logs` when `last_error` is set — so fli failing looked exactly like fli succeeding. Observed: fli 113 rows cheapest €784 → fast_flights **6** rows cheapest €957, headline price up ~€170, `system_logs` completely empty. Now sets `last_error` at **WARNING** (degraded but still serving prices) naming the primary's own error and the row count. (2) **`fast_flights` emitted unidentifiable rows.** `_to_iso` returns `""` when Google hands back a null date component — deliberate, and it was safe while `flight_key` carried `flight_number`; **plan 019 removed `flight_number` from the key and this was missed**, so `""` yields `tap air portugal||2026-08-21T22:30:00` and every flight by that airline arriving then collapses into one identity. **96 such rows reached production.** `_fetch` now drops rows lacking either timestamp and reports the count at WARNING. **The 96 historical rows are still in the DB** — deleting them is a destructive action and was left for the user to approve. Pinned by `tests/test_source_degradation.py`. General lesson: `logger.warning` never reaches `system_logs` (nothing configures a handler that writes there) — `last_error`/`last_error_level` is the only channel `/monitor` sees.
- **Kayak cadence + cross-tracker serialization (2026-08-11, `scheduler.py`)**: two defects found from live data, both fixed. (1) **Every-other-cycle drift** — `kayak_next_due_at` was measured from cycle *end* and jittered around the **full** tracker interval, so it landed after the next tick about half the time, and the end-measurement made the miss compound: Kayak refreshed every ~6h against a 3h tracker (`07:42 ran → due ~10:42 → 10:31 tick 11 min early → SKIPPED`). Now measured from `kayak_cycle_started` (captured **before** the 0-15 min sleep) and jittered around `interval * _KAYAK_DUE_MARGIN` (**0.7** → 101-151 min against a 180 min tick, ~29 min headroom). Being due early costs nothing — the tick still gates the run, so the real cadence stays ~180 min; the detection-relevant randomness is the pre-render sleep, unchanged. (2) **`max_instances=1` is per-JOB, not global** — with Kayak on trackers 20/21/22, whose jobs fire within a second of each other, two renders could drive the single-writer `data/kayak-profile` at once. `_get_kayak_render_lock()` (one lazily-created `asyncio.Lock` for the process) now wraps the `KayakSource.search` call, acquired **after** the jitter sleep so waiting doesn't serialize the sleeps too. Pinned by `tests/test_kayak_cadence.py`. **Enabling Kayak on more trackers is safe for the profile now, but each one is real traffic against a bot-detecting site** — add deliberately.
- **The Kayak timeout budget is a SUM of the waits that actually happen, at both levels (024 Phase 3, `kayak.py`)** — and it had rotted at both. (1) Plan 021 Phase 2 gave the render subprocess a `_WORKER_TIMEOUT_FACTOR (2.5) * _RENDER_TIMEOUT_S` = 112.5s budget but left `_OVERALL_TIMEOUT_S` assuming the old in-process 2x bound, so slack fell 30s -> **7.5s**. It cost real data: the 02:37 run on 2026-08-11 rendered a full 19,085-char page in 124s and then lost it mid-extraction (`outcome: error`, `extracted_rows: 0`) — nothing wrong with the page. (2) The 2.5x factor was **itself** written from a false premise: the child performs **four** sequential waits, not two — the warmup `page.goto`, the warmup dwell, the main `page.goto`, and `_wait_for_results_stable` — i.e. 140s of waiting its own code permits against a 112.5s kill cap. A *factor* hides that arithmetic, which is exactly how it rotted twice, so the factor is gone: `_WORKER_TIMEOUT_S = _WARMUP_TIMEOUT_S (20) + _MAX_WARMUP_DWELL_S (5) + 2 * _RENDER_TIMEOUT_S (90) + _WORKER_STARTUP_ALLOWANCE_S (15)` = **130s**, and `_OVERALL_TIMEOUT_S = _WORKER_TIMEOUT_S + _LLM_TIMEOUT_S + 30.0` = **220s**, slack 30s. The warmup goto now uses its own tighter `_WARMUP_TIMEOUT_S` in `kayak_render.py` (it loads the homepage, not a results page). `_MAX_WARMUP_DWELL_S` is also `KayakRenderConfig.warmup_dwell_s`'s upper bound, so the budget line cannot drift from the config it claims to bound. `tests/test_kayak_timeout_budget.py` **reads the capped waits out of `kayak_render.py`'s own source** (regex over `timeout=X * 1000` / `cap_seconds: float = X`) and asserts both that there are still three of them and that the parent cap clears their sum plus the dwell — adding a fourth capped wait fails the suite rather than silently eating the slack. **Constant-vs-constant invariants like this are the only thing that catches a tail-latency regression — a green live smoke test does not**, and the corollary this phase adds: an invariant written against a hand-counted premise is only as good as the count, so derive the premise from the code when you can.
- **Default tracker interval is 60 min (2026-08-11, was 180)** — `DEFAULT_INTERVAL_MINUTES` in `db.py` is the single source of truth; the `_SCHEMA` default and `models.py::TrackerCreate` match it, and `pages.py::add_tracker` passes it **explicitly** because the schema's own DEFAULT only applies to newly created databases and production's `trackers` table was built at 180. All 6 existing trackers were updated in place. **~30 min is the floor**: below that the 0-15 min pre-render jitter sleep stops fitting inside one tick, and three Kayak trackers serialized behind one browser profile start overlapping. Going lower would also need the jitter sleep made proportional, and would multiply the per-render LLM call against a free-tier quota.
- **Self-transfer / "hacker" fares are stripped before extraction (2026-08-11)** — Kayak labels them `Self-transfer hack`; they are two **separately ticketed** flights stitched together (`Arajet, Air Europa`, 3 stops via PUJ, €702 when the cheapest normal fare was €784). Real, printed, and they pass every guard — so they were stored as ordinary flights and, being cheapest, dominated `best_price` and permanently `historical_best_price`. `_strip_self_transfer_rows` removes the whole block (label line → the block's own result marker), running **before** `_results_section` slices so a removed block does not consume a top-N slot. **Excluded by product decision, not defect** — a missed connection is unprotected, so the price is not comparable. `TODO.md` carries surfacing them as an opt-in flagged feature; if that happens they must stay distinguishable (a `self_transfer` column, excluded from `historical_best_price`), never merged back in.
- **Off-route prices are the same class of bug as adverts (`kayak.py`, 2026-08-11)**: `_validate` only asks whether a value is *printed on the page*, never whether it belongs to the tracked route, so any real price printed for something else passes both guards. Beyond paid placements (plan 020), **nearby-airport promos** do this: `Depart from nearby VCP and save €78 … from €706 … Show all` sits at the very top of the results — **and there is an arrival-side twin, `Arrive at nearby ORY and save €160` (GRU-CDG), found only after the origin form was already fixed, so `_NEARBY_AIRPORT_START_MARKERS` carries both** —, so `_results_section`'s slice fed €706 — a **VCP** departure — into the extractor for a **GRU** tracker (observed live 2026-08-11). `_strip_nearby_airport_promos` removes the block, bounded by `_NEARBY_AIRPORT_MAX_BLOCK_LINES`; with no `Show all` terminator in range it drops **only the promo line**, never guessing how far the block runs. Also added, **precautionarily and never observed live** (0 occurrences in every captured body): `Sponsored` / `| Ad` / `Ad |` as placement starts, matched **whole-line only** (`_PLACEMENT_ALT_START_LINES`) and bounded by `_PLACEMENT_MAX_BLOCK_LINES` — a substring match would swallow every price up to the next `View Deal`, which is worse than the bug. Both strips are applied at both call sites (`_results_section` **and** inline before `_extract`, since the orchestrator's end-to-end test mocks `_extract`). Grounding still runs against the original unstripped body. See `tests/test_kayak_offroute_prices.py`.
- **Kayak's "Self-transfer hack" rows are a different product** (noticed 2026-08-11, **not** handled): several itineraries are labelled `Self-transfer hack` — Kayak stitching two separately-ticketed flights (e.g. `Arajet, Air Europa`, 3 stops via PUJ, €702 when the cheapest normal fare was €784). They are genuinely printed on the page, so grounding passes and they are stored like any other flight — and being cheapest they **dominate `best_price` and `historical_best_price`**. They also appear inconsistently in Kayak's own inventory (present 00:43, absent 02:13), which is why a user checking kayak.com by hand may never see them. Nothing is wrong with the extraction; the open question is whether a two-ticket self-transfer fare should be labelled or excluded, since a missed connection is not protected. Untracked — decide before trusting a Kayak-only all-time low.

- **`flight_key` is source-independent (plan 017 Phase 1) and flight-number-independent (plan 019 Phase 2)**: format is `f"{normalized_airline}|{departure_time}|{arrival_time}"` (3 parts, no `source` prefix, **no `flight_number`**) — `make_flight_key` in `backend/fingerprint.py`, where `_normalize_airline` collapses whitespace, then **maps the name through `AIRLINE_NAME_TO_CODE` (`backend/airlines.py`) when it is known**, and casefolds: `(AIRLINE_NAME_TO_CODE.get(normalized.upper()) or normalized).casefold()`. **Casefolding alone only bridged CASE differences (024 Phase 4)** — `TAP AIR PORTUGAL` vs `Tap Air Portugal` always merged, but Google/fli's shortened `LATAM`/`ITA` against Kayak's `LATAM Airlines`/`ITA Airways` forked one physical flight into two identities, live, in the *same* snapshot (confirmed on snapshots 7242/7238/7124/7122/7118/7117/7116). Mapped carriers now key on the IATA code (`la|dep|arr`); unmapped names (Kayak's `Multiple airlines`, `Aerolineas Argentinas`) keep the casefolded form. Keys are opaque identifiers and the `airline` **column is untouched**, so display is unaffected — mapping variants to a canonical *name* instead would need a second map to maintain and buys only prettier keys. `backend/airlines.py` is a **leaf module with no project imports** specifically because `fingerprint.py` cannot import `pages.py`, and that import direction is why the identity and the airline-facet normalisations diverged in the first place; `pages.py` now imports the same object (`_AIRLINE_NAME_TO_CODE = AIRLINE_NAME_TO_CODE`) for the logo lookup and the facet grouping. **Adding a name variant to that map silently changes `flight_key` for every row of that carrier** — it is no longer a display-only table, so a map edit means re-running the backfill. Kayak's collapsed list view prints **no flight number on any row**, so including it gave one physical flight several identities (`""`/`"N/A"`/`"unknown"`/`"AT"` across runs) and could never equal Google's `"TP 84"` for the same flight — plan 017's cross-source merge was unreachable for Kayak until this changed. `flight_number` remains a **display-only** field (still rendered in the results table's Flight column). The same physical flight quoted by two different sources (e.g. `google_flights` and `kayak`) in the same snapshot now shares one key, which is required once sources can run concurrently in one search cycle rather than as mutually-exclusive fallbacks. **Consequence: `flight_key` can legitimately repeat within a snapshot.** Every site that builds a `{flight_key: ...}` dict from `get_flight_prices_for_snapshot`'s `ORDER BY price ASC` rows must use `setdefault` (first-write-wins = cheapest), not a plain dict comprehension (last-write-wins = most expensive) — see `previous_prices`/`prev_flights`/`current_flight_map` in `pages.py::_build_detail_context`. Anywhere flight_keys are counted or color-ranked (`ordered_top_keys`, `all_flights`/`window.allFlights`, `get_sticky_top_flight_keys` in `db.py`) must dedupe to **distinct keys**, not rows — a repeated key must not consume two slots. The **results table is the deliberate exception**: it renders one `<tr>` per DB row on purpose (multi-source transparency, so the user can compare sources and pick which to book through) and must not be deduped. **Restoring an old backup: re-run `scripts/backfill_019_flight_keys.py <db>`, do not hand-write SQL.** Production was backfilled 2026-08-05 (165,884 rows; backup `data/airfare.db.bak-019`) and again 2026-08-13 for the airline-map change (237,063 of 246,986 rows rewritten, distinct keys 2198 → 2193; backup `data/airfare.db.bak-024-phase4`) with that script, which calls `make_flight_key` itself so the stored keys agree with the running code *by construction*. It is idempotent and format-agnostic, so it also repairs a restore that predates plan 017 (4-part `source|…` keys) or plan 019 (3-part `airline|flight_number|departure_time` keys) without needing to detect which. A SQL equivalent (`LOWER(TRIM(airline)) || '|' || departure_time || '|' || arrival_time`) is now **doubly** wrong — it cannot consult the airline map at all — and was already only *coincidentally* correct — SQLite's `LOWER()` is ASCII-only without ICU while Python's `.casefold()` is Unicode-aware, and `TRIM()` does not collapse internal whitespace. Those held on 2026-08-05 (40 distinct airlines, 0 non-ASCII, 0 internal double-spaces, 0 leading/trailing whitespace) but must be **re-checked, not assumed** — Kayak already emits airline names the other sources never produced (`"Azul, easyJet"`). **A seventh dedup site** (found auditing the shipped phase, not by the original grep): `history_by_key` in `_build_detail_context` merges chart points by `(flight_key, snapshot_id)` — **not** by formatted timestamp string, because two distinct snapshots can share the same second-resolution `searched_at` (e.g. two `create_snapshot` calls in quick succession) and must still render as two separate points. `get_price_history` (`backend/db.py`) selects `fp.snapshot_id` specifically to make this possible; don't drop that column if touching the query. **It must also stay `ORDER BY s.searched_at ASC, fp.snapshot_id ASC`** (the `snapshot_id` tiebreak was added in plan 019 Phase 2): the merge compares each row against `points[-1]` only, so same-snapshot rows have to arrive *adjacent*, and `searched_at` is second-resolution — ordering by it alone does not guarantee that when two snapshots share a timestamp. Plan 019's identity change made a key repeating within a snapshot **27x** more common (570 → 15,441 rows, ~9.3% of the table), so a tie now lands on colliding rows instead of passing harmlessly through. Pinned by `test_two_snapshots_sharing_a_timestamp_stay_two_points_with_a_repeated_key`. When auditing for further sites, the question is "does this assume one row per `flight_key` per snapshot?", not "is this a dict?".

- **Kayak renders out-of-process (plan 021 Phase 2, `backend/sources/kayak_render.py`)**: `KayakSource._render` no longer drives Chromium — it is a thin launcher that spawns `python -m backend.sources.kayak_render <url> <config-json> <out-path>`, waits, and reads the body from the file. **The body goes to a file, never stdout**, because Chromium and the Node driver both write to stdout. The child is a fresh interpreter that never imports fli/curl_cffi, so patchright's own internal fork is safe *there* — that is what makes this work at all (see the fork note below). The spawn seam is **`_spawn_render_worker`** (module-level in `kayak.py`), which uses `subprocess.Popen(..., close_fds=False)` — **not `asyncio.create_subprocess_exec`**, which under uvloop is fork-based. `close_fds=False` is what routes `Popen` to `os.posix_spawn`, and it is safe because Python marks its own fds close-on-exec (PEP 446). `_WorkerProcess` adapts `Popen` to the async surface `_render` uses, running the blocking calls via `asyncio.to_thread`. Timeout is `_WORKER_TIMEOUT_S` (024 Phase 3; an explicit sum of the child's four waits — see the timeout-budget note above — replacing plan 021's 2.5x factor); on timeout the child is killed **and reaped** (`kill()` then `await wait()`). Only the *browser-driving* code moved — `_launch_args`, `_context_options`, `_warmup_sequence`, `_simulate_interaction`, `_fingerprint_is_consistent`, `KayakRenderConfig` all stay in `kayak.py`, which owns their tests and `scripts/kayak_currency_picker.py`'s imports. `_wait_for_results_stable` moved and is no longer a `KayakSource` method. **Two consequences**: the config crosses as JSON argv (`asdict` → `KayakRenderConfig(**json.loads(...))`), so a field that is not JSON-serialisable would silently break the evasion bundle in production while unit tests pass — pinned by `test_render_config_round_trips_through_the_worker_contract`; and `_probe_default_user_agent`'s module-level memo is now cold on every render (fresh process), costing one extra throwaway Chromium launch per render. That memo existed to limit exposure to the driver crash, which is now root-caused and fixed, so the tradeoff is accepted. **`data/kayak-profile` is Chromium-locked — only one render at a time.** Single tracker, `max_instances=1`, 3h cadence makes that safe today; concurrency would need a profile pool. Verified live 2026-08-10: `_render` succeeded **from inside the ASGI worker** (728 bytes, 60.9s) in the same request where a bare `fork()` returned SIG11.
- **`fork()` is unsafe in the ASGI worker — this is why Kayak never rendered in production (plan 021, SOLVED 2026-08-10)**: the worker runs **uvloop**, whose `asyncio.create_subprocess_exec` is libuv's C-level `uv_spawn` and **`fork()`s** — it never reaches `os.posix_spawn`, even with `close_fds=False` (measured; under *plain* asyncio `close_fds=False` does route to `posix_spawn`, which is why this only bites in production). The worker also holds live **`curl_cffi.Curl`** objects, pulled in by `flights` (fli) via `asyncio.to_thread(client.search, ...)` in `google_flights.py`. After `fork()` the child finalises an inherited `Curl` — `__del__` → `close()` → libcurl on a handle owned by the parent — and **SIGSEGVs before `execve`**. Patchright launches its Node driver via `create_subprocess_exec`, so every in-app render died at launch with `Connection closed while reading from the driver`. **The tell that this is the bug and not something else: the kernel names the dying process `python3.12`, not `node`/`chrome`** (`dmesg` on the *Proxmox host* — unreachable from inside the unprivileged LXC). **Diagnosis technique worth reusing: `faulthandler.enable()` before forking is inherited by the child, so the child dumps the Python stack as it dies** — that is what named `curl_cffi`. **Fix: spawn with `os.posix_spawn`** (`clone(CLONE_VM|CLONE_VFORK)`, no address-space copy, so no Python finaliser ever runs in a child) — proven by a real 58s Chromium render from a worker where bare `fork()` SIGSEGV'd in the same request. A *child* process may use patchright normally: it never imports fli/curl_cffi, so its own internal fork is safe. **Any future subprocess spawn from this app must avoid uvloop's fork path.** Two traps for anyone re-investigating: (1) it is **stateful, not constant** — it needs a `Curl` pending finalisation, so a just-restarted worker can look healthy for a few seconds; (2) **a clone with a zero-tracker DB will never reproduce it**, because no fli search runs — that precaution is exactly what made ~15 hypotheses look "ruled out" across two earlier sessions. See `.agent/reports/021-phase-1-rootcause.md`.
- **uvicorn --reload and orphaned workers**: `uvicorn --reload` spawns a new worker on each code change. If a worker is mid-query when the reload fires, the C-level `sqlite3_step` is non-interruptible; the OS detaches the worker (PPID becomes 1) and it spins forever. With fast queries (ms range) the window is negligible, but with slow un-indexed queries it caused 580% CPU for 4h+. Do not leave `uvicorn --reload` running unattended against a large DB. Orphans: `ps aux | grep multiprocessing-fork` — PPID=1 + `data/airfare.db` in fds = stale worker, kill it.
- **Chromium + `--reload` orphaning (plan 017, Phase 5)**: same trap as above, heavier variant. `KayakSource._render` opens a Chromium subprocess (`async with async_playwright()` + `try/finally browser.close()`), now headful under Xvfb; if `--reload` fires mid-render, the detached worker's Chromium child can be orphaned too. `ps aux | grep chrome` alongside the existing `multiprocessing-fork` check when investigating stuck CPU/memory.
