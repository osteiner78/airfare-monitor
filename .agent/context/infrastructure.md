# Context: infrastructure

Docker, Xvfb, process handling, database indexes and logging. Read before
touching `Dockerfile`, `docker-compose.yml`, `docker-entrypoint.sh`, or
anything that spawns a subprocess.

Extracted verbatim from CLAUDE.md (plan 029).


- **Xvfb's stale lock survives a container restart (plan 019)**: `docker compose stop` kills Xvfb but leaves `/tmp` intact, so on the next `start` `/tmp/.X99-lock` exists with **no server behind it** — and `docker-entrypoint.sh`'s original `[ ! -e lock ]` guard then skipped the launch *forever*, failing every headful render with `Missing X server or $DISPLAY`. This is sharper than the "Xvfb is not supervised" note below: a restart does **not** fix it. The entrypoint now reads the pid recorded in the lock file and clears the lock plus `/tmp/.X11-unix/X99` when that process is gone. Hit for real on 2026-08-05 after the plan 019 backfill restart.

- **Logging subsystem**: `system_logs` table in SQLite, with `insert_log(level, event, tracker_id, message)`. All search events, tracker lifecycle, and notification triggers are logged. Monitor page at `GET /monitor` with auto-refresh every 30s via HTMX polling. Log functions used: `insert_log()`, `get_recent_logs(limit)`, `get_tracker_stats()`, `get_db_stats()`.

- **`ensure_db_initialized` middleware** in `main.py` is a workaround for httpx 0.28 not triggering ASGI lifespan during tests. Keep it. The `_initialized_paths` set deduplicates per unique DB path.

- **DB indexes (flight_prices)**: Two covering indexes are critical for dashboard performance. `idx_prices_snapshot_price ON flight_prices(snapshot_id, price)` is used by `get_best_price_series` (turns a 77K-row full scan into 725 snapshot-keyed index lookups) and by the `best_price`/`previous_best_price` correlated subqueries in `get_tracker_summaries`. `idx_prices_tracker_price ON flight_prices(tracker_id, price)` is used by `get_historical_best_price` (covering index — MIN resolved in-index, no table access). Both are in `_SCHEMA`. If restoring from a backup DB that predates these, run: `sqlite3 data/airfare.db "CREATE INDEX IF NOT EXISTS idx_prices_snapshot_price ON flight_prices(snapshot_id, price); CREATE INDEX IF NOT EXISTS idx_prices_tracker_price ON flight_prices(tracker_id, price);"`.

- **`fork()` is unsafe in the ASGI worker — this is why Kayak never rendered in production (plan 021, SOLVED 2026-08-10)**: the worker runs **uvloop**, whose `asyncio.create_subprocess_exec` is libuv's C-level `uv_spawn` and **`fork()`s** — it never reaches `os.posix_spawn`, even with `close_fds=False` (measured; under *plain* asyncio `close_fds=False` does route to `posix_spawn`, which is why this only bites in production). The worker also holds live **`curl_cffi.Curl`** objects, pulled in by `flights` (fli) via `asyncio.to_thread(client.search, ...)` in `google_flights.py`. After `fork()` the child finalises an inherited `Curl` — `__del__` → `close()` → libcurl on a handle owned by the parent — and **SIGSEGVs before `execve`**. Patchright launches its Node driver via `create_subprocess_exec`, so every in-app render died at launch with `Connection closed while reading from the driver`. **The tell that this is the bug and not something else: the kernel names the dying process `python3.12`, not `node`/`chrome`** (`dmesg` on the *Proxmox host* — unreachable from inside the unprivileged LXC). **Diagnosis technique worth reusing: `faulthandler.enable()` before forking is inherited by the child, so the child dumps the Python stack as it dies** — that is what named `curl_cffi`. **Fix: spawn with `os.posix_spawn`** (`clone(CLONE_VM|CLONE_VFORK)`, no address-space copy, so no Python finaliser ever runs in a child) — proven by a real 58s Chromium render from a worker where bare `fork()` SIGSEGV'd in the same request. A *child* process may use patchright normally: it never imports fli/curl_cffi, so its own internal fork is safe. **Any future subprocess spawn from this app must avoid uvloop's fork path.** Two traps for anyone re-investigating: (1) it is **stateful, not constant** — it needs a `Curl` pending finalisation, so a just-restarted worker can look healthy for a few seconds; (2) **a clone with a zero-tracker DB will never reproduce it**, because no fli search runs — that precaution is exactly what made ~15 hypotheses look "ruled out" across two earlier sessions. See `.agent/reports/021-phase-1-rootcause.md`.

- **uvicorn --reload and orphaned workers**: `uvicorn --reload` spawns a new worker on each code change. If a worker is mid-query when the reload fires, the C-level `sqlite3_step` is non-interruptible; the OS detaches the worker (PPID becomes 1) and it spins forever. With fast queries (ms range) the window is negligible, but with slow un-indexed queries it caused 580% CPU for 4h+. Do not leave `uvicorn --reload` running unattended against a large DB. Orphans: `ps aux | grep multiprocessing-fork` — PPID=1 + `data/airfare.db` in fds = stale worker, kill it.

- **Chromium + `--reload` orphaning (plan 017, Phase 5)**: same trap as above, heavier variant. `KayakSource._render` opens a Chromium subprocess (`async with async_playwright()` + `try/finally browser.close()`), now headful under Xvfb; if `--reload` fires mid-render, the detached worker's Chromium child can be orphaned too. `ps aux | grep chrome` alongside the existing `multiprocessing-fork` check when investigating stuck CPU/memory.

- **Docker/infra (plan 017, Phase 5)**: Chromium is bundled into the main image (`Dockerfile`: `RUN patchright install --with-deps chromium`, after `pip install` — was `playwright` until plan 018 Phase 2), not a sidecar — accepted tradeoff is a Chromium OOM takes the API down with it. Grew the image from 352MB to **2.13GB** (plan estimated 300-400MB; actual growth is dominated by `--with-deps`' apt closure — X11/Mesa/fonts libs — not just the ~300MB of Chromium/ffmpeg/headless-shell binaries themselves) — still comfortably inside the 16G free on `minnie`. `docker-compose.yml` now has `shm_size: 1gb` (was Docker's 64MB default — the standard fix for Chromium crashing in containers), `deploy.resources.limits` raised to `1.5G`/`2.0` cpus (was `256M`/`0.5`, confirmed via `docker inspect` before changing), and `env_file: .env` (first secret this project has needed). `requirements-dev.txt` (pytest etc.) is deliberately **not** baked into the image (`/srv/CLAUDE.md` convention) — running the suite in-container requires `docker exec airfare-monitor pip install -r requirements-dev.txt` first; that install doesn't persist across an image rebuild.
