# Context: sources, blending and scheduling

How search cycles run, how per-source results are blended for display, how
degradation is surfaced, and the passenger/party model. Read before touching
`backend/scheduler.py`, `backend/sources/fallback.py`, or
`pages.py::_build_detail_context`'s blending.

Extracted verbatim from CLAUDE.md (plan 029).


- **The party model carries AGES and derives COUNTS (`backend/party.py`, plan 028)** — the two source families disagree about what a party *is*, and the model has to satisfy both. Kayak's URL takes **ages**; both Google-side libraries take **counts by bucket** and no age at all (verified against the installed packages: `fli.PassengerInfo` and `fast_flights.Passengers` expose exactly `adults`/`children`/`infants_in_seat`/`infants_on_lap`). Buckets: age ≥12 counts as an adult, 2–11 a child, <2 an infant. **`infants_on_lap` is explicit because no age can imply it** — a 1-year-old may fly on a lap or in a purchased seat, and that is a booking choice, which is why the roadmap's original `child_ages = [6]` shape was insufficient. Google discards ages by design, so it prices a 6- and an 11-year-old identically while Kayak may not: **cross-source price agreement is only tight for adults-only parties**, and any tolerance check must loosen when children are present. **`fast_flights.Passengers` defaults every field to `0`** — constructing it empty asks Google for a party of nobody; never build it without arguments.

- **Prices are stored as the party TOTAL plus `passenger_count`, and party is FROZEN after tracker creation (plan 028)** — Kayak prints **per person** and is multiplied by `total_travellers` at extraction, which is the highest-consequence line in that plan: forget the multiplication and Kayak reads ~N× cheaper than Google and wins every headline permanently; double it and it never wins. Both directions are caught by the cross-source agreement check on a shared `flight_key` within one snapshot. The freeze exists because `historical_best_price` is `MIN` over all rows and is **never recomputed**, so a party change mid-life would compare unlike quantities forever; to track a different party, create a new tracker. Every pre-028 row is a 1-adult total and stays valid unchanged. The party is **not** part of `flight_key` — the same physical flight priced for 1 or 4 travellers is still one flight.

- **Per-source opt-in lives in `tracker_sources`, not in tracker columns (plan 028 Phase 2)** — `(tracker_id, source, enabled, next_due_at)`, replacing the `kayak_enabled`/`kayak_next_due_at` column pair, because one column pair per source does not survive a second browser source. **Only opt-in browser sources get rows**: `FallbackSource` is a composite whose secondary runs only when the primary returns nothing, so `google_flights` and `fast_flights` are not independently schedulable and are deliberately absent. Read rows with `.get(...)` and treat a missing table or row as "feature off" — Active dev guarantees a window where new code meets an un-migrated table, and the 2026-08-04 outage is what happens when that path raises.

- **Startup no longer re-searches everything (2026-08-11, `main.py::_tracker_is_overdue`)**: `_startup` registered every job with `run_immediately=True`, so every `--reload` — i.e. every edit under `backend/` — fired a live search for every active tracker. Measured: **144 snapshots in one day against ~24 expected** at 60 min x 6 trackers, 78 of them in the single hour spent editing code, against a source that had already returned zero rows once that night. Now the immediate run happens only when that tracker's latest snapshot is already older than its interval, so a genuine restart after downtime still refreshes at once while an edit-reload cycle stays silent. Missing or unparseable timestamps err toward searching. Pinned by `tests/test_kayak_dedupe_and_startup.py`.

- **Sources are BLENDED per source, not read from one snapshot (2026-08-11, `pages.py::_build_detail_context`)**: sources run on independent cadences and fail independently, so "the latest snapshot" is only the latest view from whichever sources happened to run. A Google-only cycle used to mark Kayak's rows **"missing"** — which asserts those fares vanished, when the truth was only that Kayak had not run — and because the missing-row reconstruction looked back **exactly one snapshot**, two Google-only cycles in a row dropped Kayak from the page entirely. That is why Kayak results appeared never to show up. Now `get_source_observations(tracker_id, per_source=2)` (db.py, a `ROW_NUMBER() OVER (PARTITION BY source)` window query) returns each source's two most recent observations; the page unions each source's latest rows, computes deltas **per source** against that source's own previous run, and drops a source older than `2 * interval_minutes`. **Blend by GROUP, not raw source**: `_BLEND_GROUPS` folds `fast_flights` into `google` because `FallbackSource` runs the secondary only when the primary is empty — they are alternate scrapers of one upstream, and blending them apart resurrected a stale fallback set beside fresh primary rows (same flights, two ages). **This is a read-time join and nothing is written**: carrying rows forward into new snapshots would fabricate chart points, and `historical_best_price` is `MIN` over all rows and never recomputed, so a re-inserted stale price would distort the all-time low permanently. `best_price` is the cheapest across the blended set with `best_price_is_stale`/`_age_minutes`/`_source` driving a `.price-age` badge — **this also resolves the headline-oscillation follow-up deferred by plans 019/020**, which was the same root cause. Pinned by `tests/test_blended_sources.py`. One orchestrator test was rewritten for the new model with the user's explicit approval (`test_a_source_that_did_not_run_keeps_reporting_its_own_last_view`, replacing `test_missing_flight_reconstruction_uses_cheapest_historical_price`); its surviving intent lives in `test_missing_row_still_uses_the_cheapest_quote_of_its_own_source`.

- **Two silent source degradations (2026-08-11, both fixed)**: (1) **`FallbackSource` hid fli failures.** It returned `fast_flights`' rows without setting `last_error`, and the scheduler only writes to `system_logs` when `last_error` is set — so fli failing looked exactly like fli succeeding. Observed: fli 113 rows cheapest €784 → fast_flights **6** rows cheapest €957, headline price up ~€170, `system_logs` completely empty. Now sets `last_error` at **WARNING** (degraded but still serving prices) naming the primary's own error and the row count. (2) **`fast_flights` emitted unidentifiable rows.** `_to_iso` returns `""` when Google hands back a null date component — deliberate, and it was safe while `flight_key` carried `flight_number`; **plan 019 removed `flight_number` from the key and this was missed**, so `""` yields `tap air portugal||2026-08-21T22:30:00` and every flight by that airline arriving then collapses into one identity. **96 such rows reached production.** `_fetch` now drops rows lacking either timestamp and reports the count at WARNING. **The 96 historical rows are still in the DB** — deleting them is a destructive action and was left for the user to approve. Pinned by `tests/test_source_degradation.py`. General lesson: `logger.warning` never reaches `system_logs` (nothing configures a handler that writes there) — `last_error`/`last_error_level` is the only channel `/monitor` sees.

- **Kayak cadence + cross-tracker serialization (2026-08-11, `scheduler.py`)**: two defects found from live data, both fixed. (1) **Every-other-cycle drift** — `kayak_next_due_at` was measured from cycle *end* and jittered around the **full** tracker interval, so it landed after the next tick about half the time, and the end-measurement made the miss compound: Kayak refreshed every ~6h against a 3h tracker (`07:42 ran → due ~10:42 → 10:31 tick 11 min early → SKIPPED`). Now measured from `kayak_cycle_started` (captured **before** the 0-15 min sleep) and jittered around `interval * _KAYAK_DUE_MARGIN` (**0.7** → 101-151 min against a 180 min tick, ~29 min headroom). Being due early costs nothing — the tick still gates the run, so the real cadence stays ~180 min; the detection-relevant randomness is the pre-render sleep, unchanged. (2) **`max_instances=1` is per-JOB, not global** — with Kayak on trackers 20/21/22, whose jobs fire within a second of each other, two renders could drive the single-writer `data/kayak-profile` at once. `_get_kayak_render_lock()` (one lazily-created `asyncio.Lock` for the process) now wraps the `KayakSource.search` call, acquired **after** the jitter sleep so waiting doesn't serialize the sleeps too. Pinned by `tests/test_kayak_cadence.py`. **Enabling Kayak on more trackers is safe for the profile now, but each one is real traffic against a bot-detecting site** — add deliberately.

- **Default tracker interval is 60 min (2026-08-11, was 180)** — `DEFAULT_INTERVAL_MINUTES` in `db.py` is the single source of truth; the `_SCHEMA` default and `models.py::TrackerCreate` match it, and `pages.py::add_tracker` passes it **explicitly** because the schema's own DEFAULT only applies to newly created databases and production's `trackers` table was built at 180. All 6 existing trackers were updated in place. **~30 min is the floor**: below that the 0-15 min pre-render jitter sleep stops fitting inside one tick, and three Kayak trackers serialized behind one browser profile start overlapping. Going lower would also need the jitter sleep made proportional, and would multiply the per-render LLM call against a free-tier quota.

- **Kayak wiring into the main search cycle (plan 017, Phase 3)**: `trackers.kayak_enabled` (default 0) and `trackers.kayak_next_due_at` (nullable TEXT, `NULL` = due immediately) gate a conditional Kayak call inside `search_and_store` (`backend/scheduler.py`), inserted after the existing `get_sources()` loop and before `create_snapshot` — so Kayak's rows land in the *same* snapshot as fli's, never a snapshot of their own (see the plan's "Why Kayak shares the main snapshot"). `_kayak_due(next_due_at, now)` and `_jittered_kayak_interval_minutes(base_minutes)` (±20%, floored at 1 — deliberately irregular cadence, PerimeterX is built to catch perfectly regular polling) are pure and scheduler-independent. `search_and_store` gained a `delay: bool` param controlling a 0–15 min pre-render `asyncio.sleep` before the Kayak call only (not the whole function) — pass `delay=False` for manual/test triggers, or a manual trigger blocks its HTTP response for up to 15 min waiting on a sleep nothing asked for. **All six call sites pass it explicitly, and the parameter has no default** (027 Phase 3 removed `= True`, since a default is exactly the kind of trap 024 Phase 1 had already hit once — `api.py`'s two endpoints silently missing it): `api.py::create_tracker_endpoint` (`POST /api/trackers`), `api.py::search_now_endpoint` (`POST /api/trackers/{id}/search`), `pages.py::add_tracker`, `pages.py::search_now`, `pages.py::refresh_all`, and `scheduler.py::add_tracker_job`'s own `scheduler.add_job(..., args=[tracker_id, True], ...)` registration — the one call site that had actually been relying on the default, since a real scheduled tick needs `delay=True` for its jitter. A Kayak failure (including an exception escaping `KayakSource.search`, which is caught defensively even though the source's own contract is never-raise) degrades to zero extra rows and logs `kayak_search_error` (distinct event name from the main loop's `search_error`, so `/monitor` can separate the two) at the source's own `last_error_level`; `kayak_next_due_at` always advances afterward, success or failure, so a blocked run can't hot-retry next tick. Toggled per-tracker via `PATCH /trackers/{id}/toggle-kayak` (`backend/pages.py`, mirrors `toggle_tracker_detail`; detail page only, no dashboard card control, no job-scheduling call since there is no separate Kayak job). **`AsyncIOScheduler()`'s library defaults already provide `max_instances=1`/`coalesce=True`** (confirmed via `AsyncIOScheduler()._job_defaults` at runtime) — the plan's job-stacking mitigation for a hung Kayak render needed no code change in `add_tracker_job`. **Production migration ran 2026-08-04** (`ALTER TABLE trackers ADD COLUMN kayak_enabled INTEGER NOT NULL DEFAULT 0;` + `ADD COLUMN kayak_next_due_at TEXT;`, backup `data/airfare.db.bak-017-phase3`); both are `ADD COLUMN`, so metadata-only and safe to run against the live DB without stopping the container. **Read these two columns with `tracker.get(...)`, never `tracker[...]`** — this service runs in Active dev, so a code edit is live instantly while a schema migration is confirmation-gated, guaranteeing a window where new code meets an old table. Reading with `[]` cost ~20 min of stalled collection across all 6 active trackers on 2026-08-04 (`KeyError: 'kayak_enabled'` raised straight out of `search_and_store`, killing the snapshot for every tracker, not just Kayak). The same applies to any future tracker column: a missing column must degrade to "feature off", never an exception on the main path.

- **The price row dict is built generically now, not hand-spelled (plan 027 Phase 3, `scheduler.py`)**: `search_and_store` used to construct each `flight_prices` row as a dict literal naming eleven of `FlightResult`'s fields by hand plus `flight_key` — a new field added to the dataclass with no matching key in that literal would silently never reach the database (no error, the value is just gone). It's now `{**asdict(r), "flight_key": make_flight_key(r)}`; `insert_flight_prices` already reads columns via `p.get(...)`, so extra/reordered keys are harmless. Pinned by `tests/test_scheduler.py::test_every_flight_result_field_reaches_the_stored_row`, which walks `dataclasses.fields(FlightResult)` rather than naming any field, so it covers a future field without being edited. The two near-identical `getattr(source, "last_error", ...) -> insert_log` blocks (the main `get_sources()` loop and the Kayak call) are now one `_log_source_error(event, source, tracker_id)` helper.

- **`best_source` attribution (plan 017, Phase 4)**: `get_tracker_summaries` (`backend/db.py`) gained a `best_source` correlated subquery, same shape as the existing `best_flight_number` one, selecting `fp.source` from the latest snapshot ordered `price ASC, source ASC` — the `source ASC` tiebreak matters because sources sharing a snapshot means two sources quoting the same flight at the same price is the expected case, not an edge case, and a bare price-only order would flip attribution nondeterministically between identical runs. A `source_label` Jinja filter (`backend/pages.py`, alongside `currency_symbol`/`airline_code`) maps `"google_flights"` → `"Google Flights"`, `"fast_flights"` → `"Google Flights (alt)"`, `"kayak"` → `"Kayak"`, unknown values fall back to the raw string. `results_table.html` renders it in a new Source column — the `source` field was already present on every row (including reconstructed "missing" rows, which copy the full previous row dict), so this was templating only, no context-building change.
