# Context: the Kayak source

Everything about rendering kayak.com, extracting flights from it, and the
guards that keep bad values out of the database. Read before touching
`backend/sources/kayak.py`, `kayak_render.py`, or `scripts/kayak_*`.

Extracted verbatim from CLAUDE.md (plan 029). The one-line rules that these
notes justify live in CLAUDE.md's Rules section; this file is the evidence.


- **`KayakSource` (`backend/sources/kayak.py`, plan 017)**: renders `kayak.com` with a **headful patchright** Chromium (see the evasion-bundle note below; it was headless Playwright through plan 017) and extracts flights via an LLM (DeepSeek, OpenAI-compatible API — key in `os.environ["DEEPSEEK_API_KEY"]`, read at call time, never at import time). `patchright`/`openai` are imported **lazily inside `_render`/`_extract`**, not at module load, specifically so unit tests can mock those two methods and exercise `search()`'s control flow without either package installed (real installs land via `RUN patchright install --with-deps chromium` in the Docker image). Every extracted price is grounded against the rendered page text in `_validate` before being trusted (`historical_best_price` is `MIN` over all rows and never recomputed — a hallucinated cheap price is permanent). `_LLM_MODEL` / `_LLM_BASE_URL` in `kayak.py` point at **opencode.ai**, not DeepSeek's own API — `os.environ["DEEPSEEK_API_KEY"]` is a misleading name kept for minimal diff, but the value in `.env` is actually an **opencode.ai subscription key**. `_LLM_BASE_URL = "https://opencode.ai/zen/go/v1"` and `_LLM_MODEL = "mimo-v2.5"` — the **paid Go subscription**, switched 2026-08-15 from Zen's free tier (`zen/v1`, `mimo-v2.5-free`) after the free quota began 429ing with `FreeUsageLimitError` on 22-23 of every 24 hourly cycles across 4 Kayak trackers: **one tracker's traffic fit the free cap, four did not**, and Kayak collapsed to ~5 successful runs/day for three days (2026-08-12 to 08-15) before the switch restored 96/day. `mimo-v2.5` is the same model under the paid catalog, so plan 019 Phase 3b's benchmark carries forward rather than being reopened. The docs' `opencode-go/<id>` model-id prefix is for opencode's own CLI config, **not** this endpoint — both a real call and `/v1/models` 401 on the prefixed form. Separately, the Go proxy's `deepseek-v4-flash` hit a regional gate and then a monthly cap during plan 017 Phase 6 — unrelated to the free-tier quota, but a reason not to fall back to deepseek if mimo ever needs replacing. **The model was picked by measurement, not preference** (plan 019 Phase 3b, `.agent/reports/019-phase-3b.md`: 200 offline replays, 4 candidates × 5 captured bodies × 10 runs). The rejected incumbent `deepseek-v4-flash-free` was accurate but slow in a way nothing here could fix: **the Zen proxy honours `extra_body={"thinking": {"type": "disabled"}}` only ~3 times in 10, non-deterministically**, and a thinking run burns 2,700–7,000 completion tokens to emit ~300 tokens of JSON. Completion tokens are the tell, and they are the reason for the swap: **mimo emitted only 509 or 523 tokens across all 50 runs** — two values, never a reasoning burst — so the flag cannot be ignored, because there is no reasoning mode to ignore it with. `_extract` still sends the flag (free insurance if that ever changes; pinned by a test) and still trims the body via `_results_section` (a full ~20k-char body measured 103s). **`_LLM_TIMEOUT_S = 60.0`** (was 30) fits mimo's measured 4.3–58.7s span, whose tail is network rather than reasoning — the two slowest runs returned the same 523 tokens as the fastest. That is ~2% headroom over the observed max; past it the search returns `[]` at WARNING and the next cycle retries. **The correctness trap when benchmarking extraction models**: Kayak prints `12:30 am – 5:40 pm`, and a model that reads that as 12:30 pm produces a value that parses, survives `_canonical_timestamp`, grounds its price — and is a *second `flight_key` for one physical flight*. `longcat-2.0-free` looked like the winner on latency alone (max 13.1s, tightest tail measured) and does this on 22% of runs. `scripts/kayak_model_benchmark.py`'s `_time_grounded` is the check that caught it, and plan 019 task 4.0 ported it into production `_validate`, which now drops any row whose departure **or** arrival clock time is absent from the body (measured identical to the benchmark's verdict on all 204 real replay records; it drops 1 of mimo's 250 rows, the residual misread). Two deliberate abstentions, both so the check cannot become the thing that destroys good data: an **unparseable** time is *kept* (`_canonical_timestamp` stores such a row on purpose — this check targets the misread, not parseability), and a body printing **no** recognisable clock time grounds nothing. On a 24-hour page (a pt-BR force-redirect prints `00:30`) it grounds against the 24h form instead — but the **12-hour probe runs first and wins**, because on a page printing `12:30 am` a bare `12:30` lookup matches that very line and waves the misread through. Not registered in `sources/__init__.py::get_sources()` — see "Flight source architecture" above. `search()` sets `last_error`/`last_error_level = "WARNING"` whenever `_validate` drops rows — **all** dropped (empty result, would otherwise look identical to a clean "no flights" success) or only **some** dropped (result still returned, but the message names the drop count) — because this project's observability is the `system_logs` table on `/monitor`, and `_validate`'s own `logger.warning` calls never reach it (nothing configures a stdlib logging handler that writes there). `_OVERALL_TIMEOUT_S` is derived from `_WORKER_TIMEOUT_S`/`_LLM_TIMEOUT_S` (not a bare constant) because the render step alone can consume the child's whole budget before the LLM call even starts — if changing any render/LLM timeout, the overall cap recomputes automatically, but re-check the arithmetic still leaves slack.

- **Kayak lists one itinerary once per FARE BRAND (2026-08-11)**: observed on GRU-GVA — two rows sharing `7:20 pm – 10:25 pm+1` at €641, differing only by carrier list (`"LATAM Airlines, Iberia"` vs `"LATAM Airlines"`) and brand (`"Light + Economy Cabin"` vs `"Light"`). `_first_carrier` collapses the first difference by design and `flight_key` carries no brand, so both arrive indistinguishable. `_dedupe_rows` collapses rows identical in carrier + both clock times + price, and `_OVERFETCH_ROWS` (2) compensates because **the duplicate consumed a slot on the PAGE**, inside `_results_section`'s top-N slice, before extraction — deduping alone would have returned `top_n - 1` rows. **Neither source exposes a baggage allowance** (checked live: Kayak prints bag text only in its filter sidebar plus *"Prices ... do not include baggage fees"*; `fli`'s `FlightResult`/`FlightLeg` have no baggage field, and `BookingOption.fare_name` needs an extra call). Both *do* accept it as a **search constraint** — `fli` has `BagsFilter` and `exclude_basic_economy`, Kayak has the equivalent UI filter — so comparability is best bought by constraining the query, not by parsing. - **The Kayak timeout budget is a SUM of the waits that actually happen, at both levels (024 Phase 3, `kayak.py`)** — and it had rotted at both. (1) Plan 021 Phase 2 gave the render subprocess a `_WORKER_TIMEOUT_FACTOR (2.5) * _RENDER_TIMEOUT_S` = 112.5s budget but left `_OVERALL_TIMEOUT_S` assuming the old in-process 2x bound, so slack fell 30s -> **7.5s**. It cost real data: the 02:37 run on 2026-08-11 rendered a full 19,085-char page in 124s and then lost it mid-extraction (`outcome: error`, `extracted_rows: 0`) — nothing wrong with the page. (2) The 2.5x factor was **itself** written from a false premise: the child performs **four** sequential waits, not two — the warmup `page.goto`, the warmup dwell, the main `page.goto`, and `_wait_for_results_stable` — i.e. 140s of waiting its own code permits against a 112.5s kill cap. A *factor* hides that arithmetic, which is exactly how it rotted twice, so the factor is gone: `_WORKER_TIMEOUT_S = _WARMUP_TIMEOUT_S (20) + _MAX_WARMUP_DWELL_S (5) + 2 * _RENDER_TIMEOUT_S (90) + _WORKER_STARTUP_ALLOWANCE_S (15)` = **130s**, and `_OVERALL_TIMEOUT_S = _WORKER_TIMEOUT_S + _LLM_TIMEOUT_S + 30.0` = **220s**, slack 30s. The warmup goto now uses its own tighter `_WARMUP_TIMEOUT_S` in `kayak_render.py` (it loads the homepage, not a results page). `_MAX_WARMUP_DWELL_S` is also `KayakRenderConfig.warmup_dwell_s`'s upper bound, so the budget line cannot drift from the config it claims to bound. `tests/test_kayak_timeout_budget.py` **reads the capped waits out of `kayak_render.py`'s own source** (regex over `timeout=X * 1000` / `cap_seconds: float = X`) and asserts both that there are still three of them and that the parent cap clears their sum plus the dwell — adding a fourth capped wait fails the suite rather than silently eating the slack. **Constant-vs-constant invariants like this are the only thing that catches a tail-latency regression — a green live smoke test does not**, and the corollary this phase adds: an invariant written against a hand-counted premise is only as good as the count, so derive the premise from the code when you can.

- **Self-transfer / "hacker" fares are stripped before extraction (2026-08-11)** — Kayak labels them `Self-transfer hack`; they are two **separately ticketed** flights stitched together (`Arajet, Air Europa`, 3 stops via PUJ, €702 when the cheapest normal fare was €784). Real, printed, and they pass every guard — so they were stored as ordinary flights and, being cheapest, dominated `best_price` and permanently `historical_best_price`. `_strip_self_transfer_rows` removes the whole block (label line → the block's own result marker), running **before** `_results_section` slices so a removed block does not consume a top-N slot. **Excluded by product decision, not defect** — a missed connection is unprotected, so the price is not comparable. `TODO.md` carries surfacing them as an opt-in flagged feature; if that happens they must stay distinguishable (a `self_transfer` column, excluded from `historical_best_price`), never merged back in.

- **Off-route prices are the same class of bug as adverts (`kayak.py`, 2026-08-11)**: `_validate` only asks whether a value is *printed on the page*, never whether it belongs to the tracked route, so any real price printed for something else passes both guards. Beyond paid placements (plan 020), **nearby-airport promos** do this: `Depart from nearby VCP and save €78 … from €706 … Show all` sits at the very top of the results — **and there is an arrival-side twin, `Arrive at nearby ORY and save €160` (GRU-CDG), found only after the origin form was already fixed, so `_NEARBY_AIRPORT_START_MARKERS` carries both** —, so `_results_section`'s slice fed €706 — a **VCP** departure — into the extractor for a **GRU** tracker (observed live 2026-08-11). `_strip_nearby_airport_promos` removes the block, bounded by `_NEARBY_AIRPORT_MAX_BLOCK_LINES`; with no `Show all` terminator in range it drops **only the promo line**, never guessing how far the block runs. Also added, **precautionarily and never observed live** (0 occurrences in every captured body): `Sponsored` / `| Ad` / `Ad |` as placement starts, matched **whole-line only** (`_PLACEMENT_ALT_START_LINES`) and bounded by `_PLACEMENT_MAX_BLOCK_LINES` — a substring match would swallow every price up to the next `View Deal`, which is worse than the bug. Both strips are applied at both call sites (`_results_section` **and** inline before `_extract`, since the orchestrator's end-to-end test mocks `_extract`). Grounding still runs against the original unstripped body. See `tests/test_kayak_offroute_prices.py`.

- **The three strip-block functions share one scan loop, not three (plan 027 #1, `kayak.py`)**: `_strip_self_transfer_rows`, `_strip_nearby_airport_promos` and `_strip_placements` all had the identical skeleton (find a start line, search up to a bound for a terminator, drop the whole span if found else drop only the start line) with only the predicates and the bound differing. `_strip_blocks(lines, start_pred, end_pred, max_lines) -> list[str]` is that skeleton, pure and module-level; each of the three is now a thin wrapper binding its own predicates/bound, with its **docstring and early-exit guard kept verbatim** — each guard is evidence from a separate production incident (the €806 phantom, the VCP/ORY promos, the €702 self-transfer fare) and the point of the refactor was to share the mechanical loop without collapsing that evidence into one shared docstring. Adding a fourth strip function should use `_strip_blocks` from the start rather than hand-rolling the loop again.

- **Kayak's "Self-transfer hack" rows are a different product** (noticed 2026-08-11, **not** handled): several itineraries are labelled `Self-transfer hack` — Kayak stitching two separately-ticketed flights (e.g. `Arajet, Air Europa`, 3 stops via PUJ, €702 when the cheapest normal fare was €784). They are genuinely printed on the page, so grounding passes and they are stored like any other flight — and being cheapest they **dominate `best_price` and `historical_best_price`**. They also appear inconsistently in Kayak's own inventory (present 00:43, absent 02:13), which is why a user checking kayak.com by hand may never see them. Nothing is wrong with the extraction; the open question is whether a two-ticket self-transfer fare should be labelled or excluded, since a missed connection is not protected. Untracked — decide before trusting a Kayak-only all-time low.

- **Placement stripping + airline grounding (plan 020, `kayak.py`)**: closes the two open findings above. `_strip_placements(body_text)` (module-level, pure) removes each paid-placement block — a block starts at the line containing `"This is a paid placement from"` and ends at the **next** `"View Deal"` line, with the end search starting on the line *after* the disclosure line, not on it: the disclosure line itself always ends with its own `"View Deal"` (its price sits inline), so anchoring there strips only that one line and leaves the block's other standalone price repeats behind — the exact shape of the original €806 defect. Called from `_results_section` (defense for any future direct caller) **and** inline at the `_search_inner` → `_extract` call site, because the orchestrator's own end-to-end test mocks `_extract` entirely, bypassing whatever `_results_section` does internally — stripping has to happen before the call reaches `_extract`, not only inside it. Grounding (`_validate`) still runs against the original, unstripped body. `KayakSource._airline_grounded(airline, body_text)` closes the last ungrounded third of `flight_key` (price and both clock times were already checked): the extracted carrier, normalised the same way `make_flight_key` normalises (casefold, collapse whitespace), must appear on the page — except `"multiple airlines"` (casefolded), which is unconditionally trusted rather than substring-matched, since it's Kayak's own generated row label for a multi-carrier self-transfer itinerary (verified 8 occurrences in a real captured body), not text a model could have copied from elsewhere on the page and mis-bound to a row. **Implementing this broke two pre-existing, orchestrator-owned tests** in `test_kayak_source.py` whose fixtures used carriers absent from their own body text (IATA code `"LX"` against a page printing `"SWISS"`; placeholder `"A"`/`"B"`/`"C"`/`"D"`) — every row dropped before the logic those tests actually exercise (comma-decimal price parsing, outlier-price filtering) could run. Fixtures were adapted (inputs only, assertions untouched), following the same repair plan 019 Phase 1 made to `_sample_body()` when currency verification added a precondition. **The `"LX"` vs `"SWISS"` mismatch is a live production risk, not just a fixture artefact** — if the model ever returns an IATA code where the page prints the full name, grounding will silently drop a legitimate row (plan 017 Phase 6 saw the model return `"AT"`, Royal Air Maroc's code, for a flight number under similar conditions). The fix if it happens is prompt-side (require the carrier exactly as printed) — **do not weaken or carve out the grounding check** to route around it. Watch for it during Phase 3's live cycle: the tell is a run returning fewer than the usual five rows alongside a `WARNING` naming the dropped airline. See `.agent/reports/020-phase-1.md`, `020-phase-2.md`. **Phase 3 (`.agent/reports/020-phase-3.md`) did not reach that check — status is blocked/inconclusive, not confirmed.** The only Kayak snapshot in the DB (`id=6390`, `searched_at 01:29:40`) predates both Phase 1 (`2f2e59d`, 02:14:43Z) and Phase 2 (`785d169`, 02:21:53Z) — it is the pre-fix defect run itself, not evidence the fix works. - **Kayak currency verification (plan 019 Phase 1, `kayak.py`)**: `?currency=EUR` in `_build_url` was confirmed **not honored** — falsified against 9 real captured samples (all `English / $ / United States dollar`) *and* reconfirmed with a fresh live check during this phase (a cookie-less, profile-less headless render of the same URL still renders USD; no currency-named cookie exists in the persistent profile's Cookies DB; the one currency-related XHR, `CurrencyPickerStateProviderAction`, returns the full candidate list for the picker UI, not the active selection). Since forcing can't be trusted, `_page_currency(body_text) -> str | None` reads back what was actually served — an adjacent symbol/name pair in the header chrome (`"$\nUnited States dollar"`), matched line-by-line, **not** a substring search, because the picker's candidate list puts every currency name (including "Euro") on the page regardless of what's active. `_CURRENCY_MARKERS` maps only `USD` (evidenced) and `EUR` (this project's only tracker currency); an unmapped or unreadable currency returns `None`. `_search_inner` calls this right after the block checks and before `_extract` (same cost-ordering rule as the block check: never spend an LLM call on a page about to be refused) — on mismatch *or* `None`, it sets `last_error_level = "WARNING"` and returns `[]`. `_build_url` itself is unchanged; the URL param is still sent (it's a harmless attempt) but is no longer trusted on its own. **`_search_inner`'s `record`/`body_text` are now built before `_render` is awaited**, not after — previously a render that raised or hung left the whole `try/finally` unreached, so the hardest failures (018 attempt 7) recorded no sample at all; now the `finally` always fires (sidecar `body_len: 0` on a render exception) before the exception propagates to `search()`'s outer catch-all. See `.agent/reports/019-phase-1.md`.

- **Kayak currency FORCING — solved, and it is operational state (plan 019 Part B)**: the currency is forced by **driving Kayak's picker UI once** and answering its follow-up prompt; the preference then lives in the persistent profile at `data/kayak-profile` and every later render is served EUR with **no `?currency=` reliance**. Three non-obvious steps, all of which had to be discovered: (1) `www.kayak.com` **force-redirects by egress geography** — from the Brazilian residential IP the homepage lands on `www.kayak.com.br` in Portuguese priced in `R$`; preferences are stored **per origin**, so the picker must be driven on `www.kayak.com`, reached via Kayak's own "Go to kayak.com instead." link. (2) The currency control is in the **footer**, and renders as symbol + **ISO code** (`$`/`USD`) there while the *results page header* uses symbol + **full name** (`$`/`United States dollar` — the form `_page_currency` matches); the picker's own option label is `"€\xa0Euro"` (non-breaking space). (3) **Selecting a currency is one-time until confirmed** — Kayak then asks *"Save currency for future? … Save for future / One time only"*, and closing the browser without clicking **"Save for future"** silently discards it. That missing click is exactly why the first attempt still rendered USD. Re-run `scripts/kayak_currency_picker.py set` (modes: `set` / `verify`) whenever the profile is rebuilt or `verify` reports non-EUR — **deleting `data/kayak-profile` silently reverts to USD**, after which `search()` refuses everything (safely and loudly, but the feature is inert). `_page_currency` verification is kept regardless: forcing is the attempt, verification is the guarantee. 0 blocks across the ~10 live page loads this took. See `.agent/reports/019-currency-picker-experiment.md`.

- **A tracked date's "night" includes early-morning departures on the following calendar day, up to `_NIGHT_ROLLOVER_CUTOFF_HOUR` (2026-08-13, `kayak.py`, product decision not a bug fix)**: found while investigating why a GRU-ZRH tracker for 21/08 showed a flight departing "22/08 00:45" — the raw captured Kayak page (`20260813T005700.382768.txt` lines 150/168) confirmed it's a real, printed TAP AIR PORTUGAL result via Lisbon (price/layover/duration all check out), Kayak just doesn't print a date next to a bare `"12:45 am"`, and the extraction model was observed splitting on which calendar day it belongs to across otherwise-identical runs — 6 occurrences landed on `depart_date + 1` (spanning 2026-08-11 through 2026-08-13) against many more that correctly landed on `depart_date` for the identical 00:45 clock time. First instinct was to treat the `+1` runs as the bug and force them back to `depart_date` unconditionally. **User feedback reframed it**: "a flight at 00:45 on 22/08 counts as night of 21/08 even if it is not formally correct" — i.e. bucketing an after-midnight departure under the evening-before's tracker is the *wanted* behavior, not a side effect to correct away, but it needed to be principled and bounded rather than an accidental blanket rebase. `KayakSource._rebase_departure_date` now applies only when the extracted departure is **exactly** `depart_date + 1 day` **and** its hour is before `_NIGHT_ROLLOVER_CUTOFF_HOUR` (currently `3`, the upper end of the user's stated "up to around 2-3am" — narrow to `2` if 2:00-2:59 departures should stay out); `arrival_time` shifts by the identical one-day delta so the elapsed gap the model computed is preserved. Anything outside that window (a different hour, or more than one day off) is left exactly as extracted — almost certainly an unrelated flight, not a night rolling past midnight, so silently relabeling it would be the same class of fabrication this project's grounding checks exist to prevent elsewhere. Google/fli is unaffected: its `travel_date` param constrains results to the queried calendar day server-side, so this rollover is Kayak-only by construction, not something to replicate there. Pinned by `tests/test_kayak_source.py`'s `_rebase_departure_date`/`_validate`/`search()` tests, including the exact cutoff-hour boundary. **Not retroactive** — rows already stored under the "wrong" date from before this landed keep that date; only future Kayak runs bucket under `depart_date`.

- **The rebase is now observable (024 Phase 2, `kayak.py`)**: `_rebase_departure_date` rewrites a row's identity silently by design, but a silent rewrite is also a rewrite nobody can audit if the cutoff hour or the extraction model's own behavior drifts — this project's only catch-class precedent (the two silent source degradations, the placement/off-route phantom prices) is always the same shape: a correct-looking value that was actually wrong went unnoticed because nothing surfaced it. `_validate` now returns **`(validated, rebased_count)`** — every caller must unpack the tuple, not just index `[0]` casually if adding a new call site. `rebased_count` is incremented via identity (`rebased is not row`), counting every row `_rebase_departure_date` actually rewrote regardless of whether it later survives grounding/outlier filtering, since the signal is "did the rebase fire", not "how many rebased rows made the results table". `_search_inner` always records `rebased_rows` in the sample sidecar; when it's non-zero **and no other WARNING has already been set for the attempt** (i.e. `dropped == 0`), `last_error`/`last_error_level = "WARNING"` names the count — a drop message always wins over a rebase message when both would apply, since a drop is the more serious signal. Changing `_validate`'s return type broke ~18 pre-existing call sites across `tests/test_kayak_source.py`/`test_kayak_placements.py`; all were mechanically adapted to unpack the tuple with assertions untouched (same repair pattern as the plan 019/020 fixture adaptations noted elsewhere in this file). See `.agent/reports/024-phase-2-end.md`.

- **`KayakRenderConfig` evasion bundle (plan 018 Phase 1, `kayak.py`)**: the C1–C4 anti-detection stack (PerimeterX evasion, since plan 017's Phase 6 saw 0/5 successful live extractions) is a `@dataclass` parameter object, not scattered `_render` edits — `KayakSource(config=...)` for tests/experiments, defaults to the shipped bundle. Defaults: `headless=False` (C2, live since Phase 2's Xvfb landed), `user_data_dir="data/kayak-profile"` (C3, persistent profile — already covered by the wholesale `data/` gitignore entry, no separate one needed), `locale="en-US"` pinned regardless of egress geography, `timezone_id="America/Sao_Paulo"` (must be updated by hand on relocation — the container reports UTC, so it cannot be auto-derived). - **Kayak sample capture (plan 018 Phase 2, `backend/kayak_samples.py`)**: `capture_sample(body_text, record, samples_dir)` writes `data/kayak-samples/<utc-ts>.txt` + a `.json` sidecar (record plus derived `body_len`/`select_count`/`captured_at`/`sample_path`) and returns the body path, or `None` on **any** failure — capture is telemetry, so a search must never fail because a sample could not be written. It exists because plan 017 Phase 6 never persisted rendered bodies and its five samples became permanently unre-classifiable once `_BLOCKED_MARKERS` was corrected. `KayakSource._search_inner` writes one sample per attempt in a `finally` — but **only once `_render` has returned**: it is awaited before the record is built, so a render that hangs until `_OVERALL_TIMEOUT_S` leaves *no* sample, and the attempt is missing from the sidecar set entirely (observed 2026-08-05, plan 018 Phase 3 attempt 7). Drive any experiment analysis off the runner's JSONL and join sidecars to it, never off the sidecars alone. `KayakSource.sample_context` (plain dict) is merged into the record for what only the caller knows (`attempt_n`, `egress_ip` — filled by `scripts/kayak_experiment.py`), and `last_sample_path` exposes the result. Capture is disabled by `config.samples_dir = None`; the dir is env-overridable via `AIRFARE_KAYAK_SAMPLES_DIR`, **which `tests/conftest.py`'s autouse `kayak_samples_dir` fixture points at `tmp_path`** so the suite doesn't write synthetic bodies into the real sample set. Retention is unbounded — no pruning exists yet. `_looks_blocked_structurally` (in `kayak.py`) complements `_BLOCKED_MARKERS`: blocked iff body < 2000 chars **and** no `_RESULT_MARKERS` hit. - **`scripts/kayak_model_benchmark.py`** (plan 019 Phase 3b): offline extraction-model benchmark — replays captured bodies from `data/kayak-samples/` through candidate models, **zero Kayak requests, zero DB writes**. Modes: `list` (the provider's live model ids), `verify` (one real call per id — never benchmark an id taken from a webpage or from memory, which is how plan 018's `rebrowser-playwright` and `deepseek-v4-flash` corrections happened), `bench`, `summarize` (re-scores an existing JSONL offline, so a new correctness metric can be applied to runs already collected). Not all free ids work: `ling-3.0-flash-free` rejects `response_format={"type": "json_object"}` with a 400 while a plain call succeeds. **The extraction prompt and the grounding check are now shared, not copied (plan 027 #4)**: `kayak.py::_build_extraction_user_message(body_text, top_n, depart_date)` is a module-level pure function (`_extract` calls it too), and the benchmark imports it instead of keeping a byte-copy — pinned by a characterization test in `tests/test_kayak_source.py`, since the benchmark itself has no test coverage. - **Kayak renders out-of-process (plan 021 Phase 2, `backend/sources/kayak_render.py`)**: `KayakSource._render` no longer drives Chromium — it is a thin launcher that spawns `python -m backend.sources.kayak_render <url> <config-json> <out-path>`, waits, and reads the body from the file. **The body goes to a file, never stdout**, because Chromium and the Node driver both write to stdout. The child is a fresh interpreter that never imports fli/curl_cffi, so patchright's own internal fork is safe *there* — that is what makes this work at all (see the fork note below). The spawn seam is **`_spawn_render_worker`** (module-level in `kayak.py`), which uses `subprocess.Popen(..., close_fds=False)` — **not `asyncio.create_subprocess_exec`**, which under uvloop is fork-based. `close_fds=False` is what routes `Popen` to `os.posix_spawn`, and it is safe because Python marks its own fds close-on-exec (PEP 446). `_WorkerProcess` adapts `Popen` to the async surface `_render` uses, running the blocking calls via `asyncio.to_thread`. Timeout is `_WORKER_TIMEOUT_S` (024 Phase 3; an explicit sum of the child's four waits — see the timeout-budget note above — replacing plan 021's 2.5x factor); on timeout the child is killed **and reaped** (`kill()` then `await wait()`). Only the *browser-driving* code moved — `_launch_args`, `_context_options`, `_warmup_sequence`, `_simulate_interaction`, `_fingerprint_is_consistent`, `KayakRenderConfig` all stay in `kayak.py`, which owns their tests and `scripts/kayak_currency_picker.py`'s imports. `_wait_for_results_stable` moved and is no longer a `KayakSource` method. **Two consequences**: the config crosses as JSON argv (`asdict` → `KayakRenderConfig(**json.loads(...))`), so a field that is not JSON-serialisable would silently break the evasion bundle in production while unit tests pass — pinned by `test_render_config_round_trips_through_the_worker_contract`; and `_probe_default_user_agent`'s module-level memo is now cold on every render (fresh process), costing one extra throwaway Chromium launch per render. That memo existed to limit exposure to the driver crash, which is now root-caused and fixed, so the tradeoff is accepted. **`data/kayak-profile` is Chromium-locked — only one render at a time.** 4 trackers on a 60 min cadence stay safe only because `_get_kayak_render_lock()` serialises every render process-wide (`max_instances=1` is per-JOB, not global); concurrency would need a profile pool. Verified live 2026-08-10: `_render` succeeded **from inside the ASGI worker** (728 bytes, 60.9s) in the same request where a bare `fork()` returned SIG11.
