# Context: flight identity

How two rows become the same flight: `flight_key`, the normalisation layers,
and every site that assumes one row per key. Read before touching
`backend/fingerprint.py`, `backend/airlines.py`, or anything that groups by
`flight_key`.

Extracted verbatim from CLAUDE.md (plan 029).


- **`backend/fingerprint.py` is the authoritative identity layer (plan 025)** — every normalisation that feeds a `flight_key` lives there and every other layer **defers** rather than reimplements: `normalize_airline` (first carrier before any comma → collapse whitespace → `AIRLINE_NAME_TO_CODE` variant map → casefold), `canonical_timestamp` (ISO round-trip; **unparseable values pass through on purpose** — `_validate` is the guard, not this), and `make_flight_key`, which **canonicalises its own timestamp inputs** rather than trusting callers. That last point is the rule: a source that forgets to normalise cannot produce a wrong key. Consumers: `pages.py`'s airline facet calls `normalize_airline` directly (it previously held a *copy* of the logic, and the copy had already drifted — it left a mapped code uppercased where the key casefolded it, so facet keys are now `"vy"` not `"VY"`), and `KayakSource._canonical_timestamp` is now an alias for the shared function. `KayakSource._first_carrier` **stays source-local by design** — it shapes the *displayed* airline, which is the source's business; identity is not. `_rebase_departure_date` also stays in Kayak: it answers a page-semantics question (which calendar day a printed 00:45 belongs to), and must run **before** identity is computed. **The refactor was key-preserving and verified as such** — all 261,534 stored keys recomputed, 0 mismatches (`.agent/reports/025-phase-3.md`); it was safe only because 0 stored airline values contain a comma and 0 stored timestamps are non-canonical. Re-check those two counts before folding any further normalisation in. If a new source needs its values massaged to compare, the massaging goes in `fingerprint.py`, never in the source — a source-local normalisation is invisible to the identity layer and stops applying the moment another source appears. This is the class fix for the two defects `130b205` and `d23d5a8` fixed as instances.

- **Kayak's two identity-field normalisations (plan 019 Phase 2 + task 2.6)**: both `flight_key` fields Kayak controls needed canonicalising before its rows could merge with Google's. (1) **Timestamps** — the extraction model alternates between `"2026-10-04T00:30"` and `"...T00:30:00"` for the same flight across runs, and both times are two thirds of the key, so `KayakSource._canonical_timestamp` runs them through `datetime.fromisoformat().isoformat()` (what `GoogleFlightsSource` already emits, which is what makes the two sources line up); unparseable values pass through untouched. (2) **Airline** — Kayak prints a comma-joined carrier list for multi-carrier itineraries (`"Azul, easyJet"`, `"Azul, TAP AIR PORTUGAL"`) while the Google sources use `r.airlines[0]`, a single carrier, so casefolding could not bridge them and those flights never merged. `KayakSource._first_carrier` takes the text before the first comma. No backfill was needed — all 40 distinct airline values already stored are single-carrier, i.e. already in this form. A wrong merge would require the same first carrier *and* the same departure *and* arrival time, which is the same physical itinerary. Kayak's own display loses the connecting carriers; that is the accepted cost of one identity per flight.

- **`flight_key` is source-independent (plan 017 Phase 1) and flight-number-independent (plan 019 Phase 2)**: format is `f"{normalized_airline}|{departure_time}|{arrival_time}"` (3 parts, no `source` prefix, **no `flight_number`**) — `make_flight_key` in `backend/fingerprint.py`, where `_normalize_airline` collapses whitespace, then **maps the name through `AIRLINE_NAME_TO_CODE` (`backend/airlines.py`) when it is known**, and casefolds: `(AIRLINE_NAME_TO_CODE.get(normalized.upper()) or normalized).casefold()`. **Casefolding alone only bridged CASE differences (024 Phase 4)** — `TAP AIR PORTUGAL` vs `Tap Air Portugal` always merged, but Google/fli's shortened `LATAM`/`ITA` against Kayak's `LATAM Airlines`/`ITA Airways` forked one physical flight into two identities, live, in the *same* snapshot (confirmed on snapshots 7242/7238/7124/7122/7118/7117/7116). Mapped carriers now key on the IATA code (`la|dep|arr`); unmapped names (Kayak's `Multiple airlines`, `Aerolineas Argentinas`) keep the casefolded form. Keys are opaque identifiers and the `airline` **column is untouched**, so display is unaffected — mapping variants to a canonical *name* instead would need a second map to maintain and buys only prettier keys. `backend/airlines.py` is a **leaf module with no project imports** specifically because `fingerprint.py` cannot import `pages.py`, and that import direction is why the identity and the airline-facet normalisations diverged in the first place; `pages.py` now imports the same object (`_AIRLINE_NAME_TO_CODE = AIRLINE_NAME_TO_CODE`) for the logo lookup and the facet grouping. **Adding a name variant to that map silently changes `flight_key` for every row of that carrier** — it is no longer a display-only table, so a map edit means re-running the backfill. Kayak's collapsed list view prints **no flight number on any row**, so including it gave one physical flight several identities (`""`/`"N/A"`/`"unknown"`/`"AT"` across runs) and could never equal Google's `"TP 84"` for the same flight — plan 017's cross-source merge was unreachable for Kayak until this changed. `flight_number` remains a **display-only** field (still rendered in the results table's Flight column). The same physical flight quoted by two different sources (e.g. `google_flights` and `kayak`) in the same snapshot now shares one key, which is required once sources can run concurrently in one search cycle rather than as mutually-exclusive fallbacks. **Consequence: `flight_key` can legitimately repeat within a snapshot.** Every site that builds a `{flight_key: ...}` dict from `get_flight_prices_for_snapshot`'s `ORDER BY price ASC` rows must use `setdefault` (first-write-wins = cheapest), not a plain dict comprehension (last-write-wins = most expensive) — see `previous_prices`/`prev_flights`/`current_flight_map` in `pages.py::_build_detail_context`. Anywhere flight_keys are counted or color-ranked (`ordered_top_keys`, `all_flights`/`window.allFlights`, `get_sticky_top_flight_keys` in `db.py`) must dedupe to **distinct keys**, not rows — a repeated key must not consume two slots. The **results table is the deliberate exception**: it renders one `<tr>` per DB row on purpose (multi-source transparency, so the user can compare sources and pick which to book through) and must not be deduped. **Restoring an old backup: re-run `scripts/backfill_019_flight_keys.py <db>`, do not hand-write SQL.** Production was backfilled 2026-08-05 (165,884 rows; backup `data/airfare.db.bak-019`) and again 2026-08-13 for the airline-map change (237,063 of 246,986 rows rewritten, distinct keys 2198 → 2193; backup `data/airfare.db.bak-024-phase4`) with that script, which calls `make_flight_key` itself so the stored keys agree with the running code *by construction*. It is idempotent and format-agnostic, so it also repairs a restore that predates plan 017 (4-part `source|…` keys) or plan 019 (3-part `airline|flight_number|departure_time` keys) without needing to detect which. A SQL equivalent (`LOWER(TRIM(airline)) || '|' || departure_time || '|' || arrival_time`) is now **doubly** wrong — it cannot consult the airline map at all — and was already only *coincidentally* correct — SQLite's `LOWER()` is ASCII-only without ICU while Python's `.casefold()` is Unicode-aware, and `TRIM()` does not collapse internal whitespace. Those held on 2026-08-05 (40 distinct airlines, 0 non-ASCII, 0 internal double-spaces, 0 leading/trailing whitespace) but must be **re-checked, not assumed** — Kayak already emits airline names the other sources never produced (`"Azul, easyJet"`). **A seventh dedup site** (found auditing the shipped phase, not by the original grep): `history_by_key` in `_build_detail_context` merges chart points by `(flight_key, snapshot_id)` — **not** by formatted timestamp string, because two distinct snapshots can share the same second-resolution `searched_at` (e.g. two `create_snapshot` calls in quick succession) and must still render as two separate points. `get_price_history` (`backend/db.py`) selects `fp.snapshot_id` specifically to make this possible; don't drop that column if touching the query. **It must also stay `ORDER BY s.searched_at ASC, fp.snapshot_id ASC`** (the `snapshot_id` tiebreak was added in plan 019 Phase 2): the merge compares each row against `points[-1]` only, so same-snapshot rows have to arrive *adjacent*, and `searched_at` is second-resolution — ordering by it alone does not guarantee that when two snapshots share a timestamp. Plan 019's identity change made a key repeating within a snapshot **27x** more common (570 → 15,441 rows, ~9.3% of the table), so a tie now lands on colliding rows instead of passing harmlessly through. Pinned by `test_two_snapshots_sharing_a_timestamp_stay_two_points_with_a_repeated_key`. When auditing for further sites, the question is "does this assume one row per `flight_key` per snapshot?", not "is this a dict?".

- **`_AIRLINE_NAME_TO_CODE`'s second job (024 Phase 6, `pages.py`)**: the shared name→IATA map (`backend/airlines.py`, also used by `fingerprint.py` for `flight_key` identity) has two consumers in `pages.py`, and they deliberately diverge on `LOGO_UNAVAILABLE_CODES`. `_airline_code_from_name` (the logo lookup, feeding the `airline_code_from_name` Jinja filter) looks up the code **and** gates it against `LOGO_UNAVAILABLE_CODES`, returning `""` — forcing the airline-name fallback — when the mapped code has no usable logo image. `_airline_identity` (`_build_detail_context`'s facet-grouping/checkbox identity, 024 Phase 5) looks up `_AIRLINE_NAME_TO_CODE` **directly**, deliberately bypassing that gate: a carrier with no logo image should still merge into one filter group, since the gate is a display concern, not an identity one. Route a new lookup through whichever consumer matches the job — do not merge the two or send the logo lookup through `_airline_identity` (or vice versa).
